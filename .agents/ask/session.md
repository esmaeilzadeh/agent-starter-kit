# AskIt session instructions

- Start on the AskIt path. Before starting or resuming work, run `./ask access-check` unless the session hook already checked access. If it fails, report the blocked path and stop project work until access is restored.
- For a continuation request, inspect the branch, workstream artifacts, inner-loop state, and recent commits. Resolve an explicitly named workstream first. Otherwise prefer a matching checked-out `agent/<work-id>`. Resume only its authorized stage and task. Report an explicit stop or terminal endpoint and preserve prior approvals. Ask if the target or authorization evidence is ambiguous.
- Before using any stage, classify each deliverable and state its route and evidence: feature, bug fix, investigation, review, or behavior-preserving maintenance. Separate mixed outcomes. Reproduce reported defects before editing or adding a regression. Follow `_ask/policies/workflow.md` for route boundaries, artifacts, and completion; investigation and review do not authorize implementation of findings.
- Use 00 Explore for missing facts and 01 Grill for unresolved goals, assumptions, or tradeoffs; use either or both as needed. For feature exploration, record evidence and remaining human decisions in its handoff before Grill. Skip Explore when evidence is sufficient; omit `explore-map.md` and record `Explore skipped: evidence sufficient for intent.` without rewriting earlier approved intent.
- Before labor, run `./ask check-clean`. Resolve dirty paths with the human. For feature implementation, `./ask start-work <work-id>` creates a scaffold from `develop`. Standalone maintenance uses `maintenance/<work-id>` and the workflow policy's concise record and repository verification; preserve existing Engineering Model and TaskGraph gates when already governing the work. Standalone investigation/review needs a report, not an implementation scaffold. Prepare pinned skills when needed. After changing stage or binding sources, run `./ask sync`.
- Present the complete feature intent and assumptions as **Approve** or **Request changes** choices and record the submitted choice with `./ask confirm-intent`. Derive spec details only from that authority; return unresolved product behavior choices to the human before dependent work. Use `./ask check-workstream <work-id> --implementation` for feature implementation. Follow the authorized work record, commit meaningful implementation steps, and use `.agents/ask/task-loop.md` for an active TaskGraph.
- Route consequential uncertainty through `_ask/policies/workflow.md#model-confidence-escalation`: investigate missing facts, consult on technical judgment, and ask the human for preferences or authority. Classify `uncertainty_kind` explicitly on decision requests; confidence cannot replace evidence.
- Before claiming implementation completion, run `./ask verify` and record its commit. Diagnose failures using `_ask/policies/verification.md` before choosing implementation repair, verification repair, Spec Change, or a blocker. Investigation/review completion records findings, source revisions, evidence, and limitations. For feature acceptance use `./ask check-workstream <work-id> --acceptance` and present **Accept workstream** or **Request changes**. Keep prior approvals unless What, Why, or an assumption changes.
- An explicit request to go off-path applies to the current chat only. Request routing and reproduction still apply. Read the relevant stage contracts under `.agents/ask/stages/` and policies under `_ask/policies/`.
