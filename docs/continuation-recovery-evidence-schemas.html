Continuation Recovery: Evidence Schemas

How accepted contracts, test runs, coordinator state, checkpoints, reviews, and integration evidence refer to one another—and where the current checkout breaks that chain.

1. Behavior: evidence lifecycle and recovery

C->>R: Run mapped cases on exact candidate R->>F: Write per-execution JSON and log artifacts R->>F: Write ask-test-results/v1 report R->>L: Append run summary with report digest and candidate/contract identities C->>F: Validate report, artifacts, and ledger row C->>F: Record run summary in task evidence C->>G: Checkpoint state and runtime evidence blobs G-->>C: Publish checkpoint commit and workstream ref rect rgb(247, 243, 232) Note over C,G: Interruption preserves the attempt and its run history. C->>F: Archive attempt, evidence, and execution rows in state C->>G: Publish interrupted checkpoint Rev->>F: Record reviewed reconciliation receipt for exact transition C->>F: Validate receipt against checkpoint, state, plan, candidate, and review C->>G: Reopen as a new attempt and checkpoint state end C->>G: Read retained checkpoint for preflight C->>F: Read selected report and execution ledger row C-->>C: Produce read-only preflight result, do not mutate task state Rev->>F: Record candidate-bound review C->>V: Verify TaskResult, review, contracts, and required run evidence V-->>C: Return integration evidence bound to candidate and verifier C->>G: Integrate candidate and publish final checkpoint

Key distinction: the checkpoint receipt records the checkpoint SHA and summary facts. It does not contain the checkpoint manifest, state snapshot, or evidence blobs. Recovery needs the checkpoint commit and its expected ref.

Interpretation: these are schema-shaped summaries, not a substitute for the validators. For example, attempt_history is nested in coordinator state, while the reconciliation receipt is a separate JSON file; the checkpoint manifest is stored inside a Git commit whose tree carries the state and runtime artifact bytes.
